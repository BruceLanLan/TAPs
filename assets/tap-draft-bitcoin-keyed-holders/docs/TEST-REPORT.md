# Test report for the Bitcoin-Keyed Holders draft

These are the parts of the Test Cases section that describe evidence rather than vectors, moved here so that the TAP keeps to what an implementation must reproduce. Paths are relative to the package root (`assets/tap-draft-bitcoin-keyed-holders/` in the TAPs repository).

## Independent signer

12 signatures made with `bip322-js` 4.0.0, a BIP-322 library used by web wallets, for the §5.1 and §5.2 messages of holders of the check's own test keys (`independentLibrary` in `vectors/vectors.json`), and 17 for the §5.3 messages of the batch cases (`tools/wallet-lib-check/`), are accepted by the reference tests, which also check them against the deployed holder and execute every batch with them; the same library with a flipped character or another message is rejected. `bip322-js` 4.0.0 and 3.0.0 also signed a §5.3 text of the greatest possible length (2,239 bytes), which the reference verifier accepted. This shows that a signer other than this repository's produces accepted signatures; it is not a wallet test.

## Differential test against an independent verifier

4,318 cases made with `bip322-js` 4.0.0 for the P2TR and P2WPKH test keys (`vectors/diff-fuzz-corpus.json`, built by `tools/wallet-lib-check/diff-fuzz.mjs`): 68 unmodified signatures for 34 texts of every kind (empty, long, multi-byte, control characters) and mutations of them (bit flips, inserted, deleted and truncated bytes, trailing bytes, every sighash type of interest, high `s`, non-minimal and BER-length DER, `r` or `s` of 0 or n, uncompressed, hybrid and other keys, item counts, `r + p` and negated `s` for Schnorr, another key's signature). The reference test requires that the holder's library accepts no case that `bip322-js` rejects (it accepts 203 and all 68 unmodified signatures, every one of them also accepted by `bip322-js`) and it reports the other direction: `bip322-js` accepts 568 cases that §6.1 refuses, namely 382 with bytes after the witness, 170 P2TR signatures with a sighash byte other than `0x00` and `0x01`, and 16 with a changed length, key-length or sighash byte that `bip322-js` does not check.

## Real wallets

four browser-extension wallets, called through their own message-signing interfaces with the BIP-322 "simple" format named explicitly, signed for one P2TR and one P2WPKH address (derived from the public BIP-39 test mnemonic `abandon … about`; they must never be funded), for the holders of the creation code of §3.2: UniSat 1.7.22 (2026-10-10, `window.unisat.signMessage(message, "bip322-simple")`), and Xverse 2.9.3, Leather 6.114.0 and OKX Wallet 4.18.1 (2026-10-11; `request("signMessage", {…, protocol: "BIP322"})`, `request("signMessage", {…, paymentType})` and `okxwallet.bitcoin.signMessage(message, "bip322-simple")`). For each address each wallet signed a §5.1 message (156 characters), two §5.2 messages (a transfer of a real ERC-721 token, 273 characters, and an empty call at nonce 1, 268) and three §5.3 messages (8 token transfers, 1,329 characters; a transfer, a coin transfer and a transfer with a tip, 610; and a batch with every number at its maximum, 2,239, the longest text `executeBatch` can accept on a chain with a 20-digit chain ID); Xverse, Leather and OKX also signed a 4,000-character text that is not a TAP message, and every wallet accepted every length. The 48 TAP signatures and 6 probe signatures all decode under §6.1 without any change (Xverse and Leather return the base64 string as `result.signature` of a JSON-RPC response, UniSat and OKX return the string itself; taking the field out is the wallet's API, not part of this TAP; no wallet added `smp`) and all verify: P2TR witnesses are 66 bytes with SIGHASH_DEFAULT, P2WPKH witnesses 107 or 108 bytes with strict DER, low `s` and SIGHASH_ALL, and for the same P2WPKH address and text the four wallets' signatures are identical byte for byte (RFC 6979). The vectors are `vectors/wallet-unisat-1.7.22.json`, `vectors/wallet-xverse-2.9.3.json`, `vectors/wallet-leather-6.114.0.json`, `vectors/wallet-okx-4.18.1.json` and the matching `-batch.json` files, built from the wallets' raw output by `tools/make_wallet_vectors.py` and `tools/make_wallet_matrix_vectors.py`, which rebuild every text and check every signature; `vectors.json` also keeps the raw outputs as the wallet APIs returned them. The reference tests deploy both holders through the proxy at their addresses and accept every signature of every wallet: through `isValidSignature` (refused with one byte changed or for another digest), through `execute` (moving a token, then the empty call) and through `executeBatch` (moving the tokens and paying the tip; the longest text up to its nonce overflow, a state no holder can reach). On local forks of BNB Smart Chain the signatures were also used against the deployed holders: `isValidSignature`, `execute` moving a real ERC-721 token and the empty call, and the two executable batches moving their tokens; each replay was rejected (`interop/unisat-extension/`, `interop/wallet-matrix/`). What the wallets did otherwise: called without a type, OKX Wallet returned a 65-byte BIP-137 signature, which the holder refuses (kept in `vectors.json`); for a P2SH-wrapped address Xverse returned a witness-only signature that is not a valid simple signature, Leather refused the address type and OKX Wallet failed with an error; their confirmation windows showed the text in full (UniSat, in a scrollable box), after one line until opened (Xverse), only behind a "Data" link (OKX Wallet), or in full but with long hex fields cut off at the right edge until scrolled sideways (Leather). UniSat's signatures of 2026-10-09 for the holder addresses of the earlier draft, and of a candidate batch build, are kept under `vectors/legacy/`; the reference tests install the current code at those addresses and accept them as well.

## Reproducible build

two builds from a clean cache produced creation code with the `keccak256` of §3.2.

## Security review

the reference tests include the tests written in the adversarial reviews that the author organized on 2026-10-08, 2026-10-10 and 2026-10-13; none of them is an audit by a third party. They are differential tests of the BIP-340 construction against a plain secp256k1 implementation, fuzzing of the DER parser and of `isValidSignature` with malformed input, message injectivity, reentrancy, gas and deployment; one of them checks that the callee of `execute` receives at least `callGas`, with and without value. The last review added tests that §5.1 approvals cannot be revoked, of the shape of a cancelling call, of the replay of a signature across forks that share a chain ID, and a sweep of the outer gas limit for a batch of 8 value transfers to new accounts (no partial result at any limit); it also ran the shipped runtime on the three live chains through `eth_call` with a state override (`scripts/live_conformance.py`).

## Equivalence with earlier builds

differential tests run the creation code of the earlier draft (`keccak256` `0xb09310a5…d4a7`) and the current one at the same address on the same inputs, and require the same results, return or revert data, events, nonce and balances for `isValidSignature`, `execute`, the messages, the constructor and random calldata (200,000 fuzz runs each). Likewise for `executeBatch` and `batchMessage` against a candidate build of the batch extension (200,000 runs), and for a batch of one call against `execute` of the same call (200,000 runs, with the revert data of a failed callee wrapped in `BatchCallFailed(0, …)` and cut to 256 bytes, and no return data from `executeBatch`).

## Batch properties

fuzzed with signed random batches of 1 to 8 calls (200,000 runs): a failed batch changes nothing; a successful one uses one nonce, pays the tip once to `msg.sender`, spends exactly the values it names, emits one `Called` per call in order, and cannot be replayed; the same signature fails for a reordered, shortened or lengthened batch. The batch message parses back to exactly the batch that produced it and equals an independent rendering (100,000 runs each for three such properties). A relayer that supplies the least gas with which a batch succeeds gives every callee what a generous relayer gives it, for call data of up to 24,000 bytes per call. Eight callees that each return 200,000 bytes cost the holder nothing beyond what they pay themselves within their `callGas`, and a callee that reverts with 300,000 bytes still yields `BatchCallFailed` with the first 256 bytes to a relayer that supplies the signed gas plus a small margin.


## Test run

`docs/TEST-RUN-2026-10-13.txt` is the list of the tests of one run on 2026-10-13: 231 tests passed, 0 failed (65 fuzz tests, 512 runs each by default; the differential and batch-property tests set 100,000 or 200,000 runs with a `forge-config` comment in their files, `contracts/test/diff/`, `contracts/test/batch/BatchFuzz.t.sol`, `contracts/test/batchlab/`).

## Reproducible build

With Foundry 1.8.3 and solc 0.8.28 (the settings of `contracts/foundry.toml`): `cd contracts && forge clean && forge build`, then the `bytecode.object` of `out/BitcoinKeyedHolder.sol/BitcoinKeyedHolder.json` equals `vectors/creation-code.hex` (7,869 bytes, `keccak256` `0x4bc9698a…c4f`). Two builds from a clean cache gave the same bytes.
