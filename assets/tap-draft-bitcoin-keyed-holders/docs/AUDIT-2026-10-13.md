# Second adversarial review round (2026-10-13, organised by the author, not a third-party audit)

Scope: this repository at `3f93e07` (read-only). Method: a reviewer working separately from the implementer (not a third party) added 8 tests in a copy (`contracts/test/Round2.t.sol`) and ran read-only state-override checks on three chains (no transaction was sent). This round was also organised by the author; it is not an audit by a third-party firm. Re-check in this repository: the 8 tests were rerun in a clean copy and all pass; `scripts/live_conformance.py` was rerun and everything matches expectations; all 229 tests in the repository pass.

## Conclusion

No new Critical, High or Medium findings. No attack was constructed from the angles of replay, witness-parsing bypass, `ecrecover` forgery, batch atomicity and tip ordering, or CREATE2 collision. What this round leaves are design and documentation items, plus one evidence gap (the three-chain claims had previously only been verified on anvil forks), which has been closed.

## Items

| ID | Severity | Content | Handling |
|---|---|---|---|
| V1 | Low (design/docs) | The §5.1 signature is permanent and cannot be revoked: the holder has no means of revocation; burning the nonce, emptying the holder or signing something else does not invalidate it. Test `test_51_approval_is_irrevocable` | The bytes are fixed, so documentation only: Security Considerations states it, and interfaces must explain it before requesting a §5.1 signature; a future version could add `revoke(bytes32)` |
| V2 | Low (docs) | "Send a cancellation at the same nonce first" is a race that can be lost (the holder of the original signature sends first, and the cancellation fails with `BadSignature()`); the most natural cancellation shape (self-call, callGas 0) always fails. Tests `test_cancel_race_original_wins`, `test_cancel_call_shapes` | Documentation: cancellation is only best effort, and a short deadline is the real control; a canonical cancellation shape is given |
| V3 | Info | Two forked chains with the same chainId accept the same signature (when the nonces match). Test `test_same_chainid_fork_replays` | One sentence in the documentation |
| V4 | Info (evidence gap, closed) | The three-chain claims had only been verified on anvil forks; now all signature vectors were run on real nodes of BSC, Base and X Layer with `eth_call` state overrides (16/16, 4/4, 3/3), and the bytecode of precompiles 0x01/0x02/0x03/0x05, PUSH0 and the deterministic deployment proxy was confirmed to be the same on the three chains | Script `scripts/live_conformance.py` |
| V5 | Info (negative result) | A 65-byte witness accepts only 0x01; P2WPKH parity flips and uncompressed public keys are rejected; P2TR and P2WPKH holders do not accept each other's signature for the same digest; the two init code lengths differ, so there is no CREATE2 collision | Added to tests |
| S1 | Info (not reproduced) | If a circuit leaves the holder and comes back, an old §5.1 signature is valid for it again as long as the delegation has not expired | Written into Security Considerations |
| S2 | Info | `receive()` without `fallback()`: a native-coin transfer with calldata reverts, so ERC-777-style tokens cannot be received | Known, not changed |
| S3 | Info | Hardware signers and texts longer than 2,239 bytes are untested | Stated in the documentation |

## Other documentation fixes in the same round (from another reviewer)

- §4 gets point 5: only the address derived from the canonical init code is a holder; clients must not display, or send assets to, addresses deployed from other encodings (review finding F-03).
- §6.1: non-zero unused base64 bits changed from "may reject" to "must not reject" (the reference implementation already accepted them).
- `MAX_CALL_GAS`: states that `callGas` must be less than 2^64.
- The contradiction between Rationale and Security Considerations is removed: the contract itself is not upgradeable, but its use depends on upgradeable TapeOut contracts, so it goes to Candidate under TAP-01 §5.1.
- Security Considerations adds the single-key upgrade authority of DeWebHub, SiteRegistry and DomainBinding (read on 2026-10-12; the authorisation source code was not read).
