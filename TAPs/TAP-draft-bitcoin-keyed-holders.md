# TAP-TBD: Bitcoin-Keyed Holders

> **Status of this draft.** The creation code, and with it every holder address and vector, is provisional until Review (Backwards Compatibility): nothing of value should be sent to a holder address before then. Editors are asked to rule on two points: whether a normative bytecode file (§3.2) is acceptable in a TAP, and whether the type is Application or Standards (Rationale, "Why Application").

## Summary

Someone who has only a Bitcoin wallet can own a TapeOut circuit and run its services by signing messages in the wallet they already use.

## Abstract

This TAP defines a holder contract whose only authority is one Bitcoin address, P2TR key path or P2WPKH. Its creation code is fixed byte for byte and it is deployed with the deterministic deployment proxy, so the same Bitcoin address has the same holder address on every chain where that proxy exists (BNB Smart Chain, Base and X Layer; Deployments), computable before deployment. The contract answers EIP-1271 `isValidSignature` with a BIP-322 "simple" signature over a fixed ASCII message that names the holder, the chain and the digest, and it makes calls on its own behalf when the Bitcoin address signs a second message format that names the call in full, or a third that names an ordered batch of up to eight calls, which are made all or nothing. It has no owner, no upgrade path and no recovery. A TapeOut circuit transferred to it is held by the Bitcoin key, and a TAP-11 client that supports EIP-1271 holders (TAP-11 §4.4 item 2) accepts delegations by it without change.

## Motivation

Every authority in TapeOut is an EVM account: a circuit belongs to `ownerOf(#ID)`, the holder authorises a container's service signer under TAP-11 §4, and the container acts for whoever holds the circuit (TAP-10). Someone whose keys are Bitcoin keys cannot hold a circuit without creating, funding and safeguarding a second, EVM key.

TAP-11 §4.4 already accepts a holder that is a contract answering EIP-1271, and an EVM contract can check Bitcoin signatures cheaply: BIP-340 through the `ecrecover` precompile, ECDSA directly, and the hashing of BIP-322 with the `sha256` and `ripemd160` precompiles. What is missing is one agreed contract and one agreed set of messages. Without them every implementation chooses its own message text and encoding: wallets cannot show users what they are approving, relayers and TAP-11 clients cannot recognise the holder, a Bitcoin address maps to a different holder address in each implementation, and a signature made for one implementation may be valid for another.

## Specification

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT" and "MAY" in this document are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in all capitals.

### 1. Terms

- **Bitcoin address**: a mainnet segwit address (human-readable part `bc`, BIP-173 and BIP-350) of one of the two supported kinds (§2). Its **scriptPubKey** is the output script it encodes. A client **MUST NOT** derive a holder from an address with another human-readable part (for example a testnet `tb1…` address), although the contract sees only the scriptPubKey and cannot tell them apart.
- **Holder**: an instance of the contract of §3, deployed as §4 specifies. TAP-10 and TAP-11 also call the owner of a circuit (`ownerOf(#ID)`) its holder; in this TAP "holder" is the contract, and the other sense is written "the circuit's owner".
- **Simple signature**: a BIP-322 "simple" signature: the consensus serialization of the witness stack of the BIP-322 `to_sign` transaction.
- **Relayer**: any EVM account that sends a transaction to a holder. Relayers have no authority over a holder.
- **Hex** in a message is lowercase. **Decimal** is base 10 without leading zeros (`0` for zero). `‖` is concatenation.

### 2. Supported Bitcoin addresses

| Kind | Address | scriptPubKey | Key |
|---|---|---|---|
| P2TR, key path only | `bc1p…` (bech32m, witness version 1) | `0x51 0x20` ‖ 32-byte output key | The BIP-341 output key. A wallet that uses a BIP-86 single key signs with the tweaked secret key |
| P2WPKH | `bc1q…` (bech32, witness version 0, 20-byte program) | `0x00 0x14` ‖ 20-byte key hash | A compressed secp256k1 key whose `RIPEMD-160(SHA-256(key))` is the key hash |

Other kinds (P2PKH, P2SH, P2SH-P2WPKH, P2WSH, taproot script paths, multisig) are not supported.

Event `Called(uint256 indexed nonce, address indexed target, uint256 value, bytes32 dataHash)`, topic `0x9fe7115c2392aead0d86cee85b52169b9fa5e170aa1bebd3f05c04e35df6575d`. Errors `UnsupportedScript()` (`0xa7a487cc`), `Expired()` (`0x203d82d8`), `BadSignature()` (`0x5cd5d233`), `NoCode()` (`0xf046a714`), `InsufficientGas()` (`0x1c26714c`), `TipFailed()` (`0xd99123cb`), `BadBatch()` (`0x86bdc25c`), `BatchCallFailed(uint256 index, bytes returnData)` (`0x651ab1b3`), where `returnData` holds at most the first 256 bytes of the failed call's revert data (§6.4).

`execute` and `executeBatch` are not payable: they revert, with empty return data, when they receive native coin. `Called` records neither `callTip` nor the relayer; an indexer that needs them reads the `execute` or `executeBatch` calldata, or the call trace when the holder was called by a contract. `executeBatch` emits `Called` once for each of its calls (§6.4 step 9).

The contract has no owner, no administrator, no upgrade path, no `selfdestruct` and no other way to move assets than §6.3 and §6.4.

#### 3.2 Creation code

The creation code is the 7,869 bytes in `assets/tap-draft-bitcoin-keyed-holders/vectors/creation-code.hex`, whose `keccak256` is `0x4bc9698ad9224fefccd7ba5d7205c1c0e8e9117eb53257873e64fae37f499c4f`. It is the output of the reference source (Reference Implementation) compiled with solc 0.8.28, EVM version `shanghai`, optimizer on with 200 runs, `viaIR` on, no metadata hash and no CBOR metadata. Implementations **MUST** deploy exactly these bytes; a holder deployed from other bytes is not a holder of this TAP, even if it behaves the same. The creation code is normative for the behaviour of a holder: §5 and §6 describe that behaviour, and where they differ from what the code does, the code prevails for deployed holders and the difference is an erratum to this TAP. A client **MUST NOT** rely on behaviour that the text states and the code lacks.

### 4. Deployment and address

1. The **init code** for a Bitcoin address is the creation code ‖ the ABI encoding of the constructor argument `bytes scriptPubKey`: `uint256(32)` ‖ `uint256(L)` ‖ scriptPubKey padded with zero bytes to a multiple of 32 bytes, where `L` is 34 (padded to 64 bytes) or 22 (padded to 32 bytes).
2. A holder is deployed by calling the deterministic deployment proxy at `0x4e59b44847b379578588920cA78FbF26c0B4956C` with calldata `bytes32(0)` ‖ init code. The proxy runs `CREATE2` with salt 0.
3. The holder address is therefore `keccak256(0xff ‖ 0x4e59b44847b379578588920cA78FbF26c0B4956C ‖ bytes32(0) ‖ keccak256(init code))[12:32]`. It depends only on the scriptPubKey, so a Bitcoin address has the same holder address on every chain where the proxy exists.
4. Anyone **MAY** deploy any holder; deploying gives the deployer no authority. Tokens **MAY** be sent to a holder address before it is deployed, and are controlled by the Bitcoin key once it is. A client **MUST NOT** show a holder address, or accept assets for it, on a chain where the deterministic deployment proxy does not have the code given in Deployments or where the creation code cannot be deployed (it needs the `shanghai` EVM version, §3.2): assets sent there are stranded.
5. Only the address derived in item 3 from the init code of item 1 is the holder of a Bitcoin address. The constructor also accepts other encodings of the same scriptPubKey (other padding, trailing bytes, other offsets), and these deploy working contracts at other addresses. A client **MUST NOT** show such an address as the holder of a Bitcoin address, and **MUST NOT** send assets to it.

### 5. Messages

The three messages are ASCII text. `H` is the holder address and `C` the chain ID (`block.chainid`), and every message starts with the prefix

`TapeOut Bitcoin-keyed holder 0x` ‖ hex(`H`, 40 digits) ‖ ` on chain ` ‖ decimal(`C`)

#### 5.1 Approving a digest

prefix ‖ ` signs 0x` ‖ hex(`digest`, 64 digits)

#### 5.2 Making a call

prefix ‖ ` calls 0x` ‖ hex(`target`, 40 digits) ‖ ` with value ` ‖ decimal(`value`) ‖ ` and data 0x` ‖ hex(`keccak256(data)`, 64 digits) ‖ `, gas ` ‖ decimal(`callGas`) ‖ `, tip ` ‖ decimal(`callTip`) ‖ `, nonce ` ‖ decimal(`callNonce`) ‖ `, valid until ` ‖ decimal(`deadline`)

`callGas` is the gas argument of the call (§6.3), `callTip` an amount of the chain's native coin, in its smallest unit, that is paid to the account that relays the call (§6.3), `callNonce` the holder's `nonce` at the time of the call (§6.3), and `deadline` a Unix time in seconds. Example (informative), from the test vectors:

```
TapeOut Bitcoin-keyed holder 0x750d22d8b6dd3168c2a4a2efddd44a8bfe362647 on chain 56 calls 0x00000000000000000000000000000000000000c1 with value 0 and data 0xcb756a7ba059624ae79c6fcf7896d07f3e5ccee5f7761b242961ec10d8ce9e0a, gas 100000, tip 0, nonce 0, valid until 2000000000
```

#### 5.3 Making several calls

A **batch** is an ordered list of K calls, where 1 ≤ K ≤ 8, together with one `callTip`, one `callNonce` and one `deadline`. Call number i (counted from 1) has a `target_i`, a `value_i`, `data_i` and a `callGas_i`, with the meanings of §5.2. The message is

prefix ‖ ` makes ` ‖ decimal(K) ‖ ` calls:` ‖ C_1 ‖ … ‖ C_K ‖ ` tip ` ‖ decimal(`callTip`) ‖ `, nonce ` ‖ decimal(`callNonce`) ‖ `, valid until ` ‖ decimal(`deadline`)

where each C_i is

` (` ‖ decimal(i) ‖ `) 0x` ‖ hex(`target_i`, 40 digits) ‖ ` with value ` ‖ decimal(`value_i`) ‖ ` and data 0x` ‖ hex(`keccak256(data_i)`, 64 digits) ‖ `, gas ` ‖ decimal(`callGas_i`) ‖ `;`

The message uses only the bytes 0x20 to 0x7e, so it has no line breaks. The calls are numbered from 1 in the message; `BatchCallFailed` reports the zero-based position. Example (informative), from the test vectors (the message is one line; it is wrapped here):

```
TapeOut Bitcoin-keyed holder 0x750d22d8b6dd3168c2a4a2efddd44a8bfe362647 on chain 56 makes 3 calls: (1) 0x00000000000000000000000000000000000000c1 with value 0 and data 0xcb756a7ba059624ae79c6fcf7896d07f3e5ccee5f7761b242961ec10d8ce9e0a, gas 100000; (2) 0x00000000000000000000000000000000000000b0 with value 1000000000000000 and data 0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470, gas 0; (3) 0x00000000000000000000000000000000000000c1 with value 0 and data 0x07a2551185fe6bfd9f6a91fbba3395156e3e998a596b3530d05db596845e0f03, gas 100000; tip 10000000000000000, nonce 0, valid until 2000000000
```

The message has 123 + |C| + |T| + |N| + |D| + Σ_i (142 + |v_i| + |g_i|) bytes, where |x| is the number of decimal digits of x, and C, T, N and D are the chain ID, tip, nonce and deadline: 142 bytes per call plus the digits of its value and gas. A call with value 0 and gas 100000 adds 149 bytes; a batch of 8 such calls on chain 56 with tip 0, nonce 0 and a 10-digit deadline is 1,329 bytes. Since `executeBatch` accepts only `callGas_i` < 2^64 and `deadline` < 2^64, any batch that it can accept has a message of at most 2,219 + |C| bytes. What a client may not ask a wallet to sign is stated in §8. A client **SHOULD NOT** use a batch of one call: its message is longer than that of §5.2 and `executeBatch` costs more gas than `execute` for one call.

Each hex field has a fixed width, and each decimal field is followed by a literal that starts with a byte that is not a digit (` `, `)`, `,` or `;`) or ends the message. The number of calls is written before the calls, and every call carries its position. A message of §5.3 can therefore be parsed in only one way, and two batches that differ in any field, in the order of their calls or in their number of calls have different messages. After the prefix, whose chain ID is always followed by a space, §5.1 continues with ` signs`, §5.2 with ` calls` and §5.3 with ` makes`, so no message of one kind equals a message of another kind.

### 6. Signatures and authority

#### 6.1 Signature encoding and checking

`sig` is the simple signature (§1) of the message by the holder's Bitcoin address, as raw bytes. Wallets usually show it as base64, which BIP-322 at the commit in `requires` may precede with the three ASCII characters `smp`. To obtain `sig`, a client **MUST**, in this order: remove leading and trailing ASCII whitespace (space, tab, carriage return, line feed); reject an output that then begins with `ful` or `pof` (BIP-322 full signatures and proofs of funds, which this TAP does not support); remove a leading lowercase `smp` if present; and decode the rest as base64 (RFC 4648 §4, with padding: a length that is not a multiple of 4, `=` anywhere but the last one or two characters, and any other character, including whitespace inside it, are rejected). A client **MUST NOT** reject base64 whose unused trailing bits are not zero: the decoded bytes are what is verified, so the text encoding does not matter.

A holder **MUST** accept `sig` if and only if it is a valid simple signature of the message under BIP-322 for its scriptPubKey, restricted as follows:

- **P2TR**: `sig` is exactly `0x01 0x40` ‖ 64-byte signature (SIGHASH_DEFAULT) or exactly `0x01 0x41` ‖ 64-byte signature ‖ `0x01` (SIGHASH_ALL). The BIP-341 key-path signature message is built for `to_sign` (one input spending `to_spend:0`, amount 0, sequence 0; one output of value 0 with script `OP_RETURN`; version 0; lock time 0) and verified under BIP-340 against the output key, except that a holder **MUST** also reject the signature when the BIP-340 challenge e is 0 (BIP-340 as written has no such rule; the difference arises with probability about 2^-256 for honest inputs, Rationale). An output key whose x-coordinate is at least the group order n never occurs in a holder, because the constructor refuses it (§3.1).
- **P2WPKH**: `sig` is `0x02` ‖ `length` ‖ (DER signature ‖ `0x01`) ‖ `0x21` ‖ 33-byte compressed key, and nothing else: `length` is one byte from 9 to 73, and `sig` is exactly 2 + `length` + 34 bytes. The DER encoding **MUST** be strict (BIP-66: positive, minimal integers), `s` **MUST** be at most n/2, the key **MUST** be a compressed point on the curve (first byte `0x02` or `0x03`), its hash160 **MUST** equal the key hash, and the ECDSA signature is verified over the BIP-143 signature hash with SIGHASH_ALL.

An accepted P2TR `sig` is 66 or 67 bytes. An accepted P2WPKH `sig` is 65 bytes or shorter only if the DER integers `r` and `s` together take at most 22 bytes, which does not happen for honestly made signatures, whose `r` and `s` are close to 256 bits. For any signature that a wallet can make, a TAP-11 client therefore does not read a holder's signature as ECDSA (TAP-11 §4.4 treats only 65-byte signatures that way) and reaches EIP-1271. Conversely, a wallet output that decodes to 65 bytes is not a simple signature: it is typically a BIP-137 message signature, which some wallets return when the request does not name the BIP-322 format (§8). A client that obtains a 65-byte `sig` **SHOULD** refuse it and tell the user that the wallet made another kind of signature, instead of passing it on, where a TAP-11 client would read it as ECDSA and report a wrong signer.

#### 6.2 `isValidSignature`

Returns `0x1626ba7e` if `sig` is valid (§6.1) for the message of §5.1 with this `digest`, and `0xffffffff` otherwise. It is `view` and never reverts on a malformed `sig` of any length, given enough gas: a valid signature costs about 15,000 to 21,000 gas, and a caller **SHOULD** supply at least 30,000.

#### 6.3 `execute`

1. If `block.timestamp > deadline`, revert with `Expired()`.
2. If `sig` is not valid (§6.1) for the message of §5.2 with `callNonce` equal to the current `nonce`, revert with `BadSignature()`.
3. If `data` is not empty and `target` has no code, revert with `NoCode()`. An account that carries an EIP-7702 delegation has code (the 23-byte delegation designator) even when the address it delegates to has none, so this check is a guard against mistyped targets and not a guarantee that anything will run.
4. Increase `nonce` by one (a nonce of 2^256 − 1 cannot be increased: the call reverts).
5. Let `need` be max(⌊`callGas` × 64 / 63⌋, `callGas` + 2,500) + `extra` (integer division), where `extra` is 3,100 when `value` is 0 and 37,100 otherwise (room for a cold account access, a value transfer and a new account). If the gas left is less than `need`, revert with `InsufficientGas()`. The `extra` of 3,100 covers one cold access; a call with empty data and value 0 into an account that carries an EIP-7702 delegation costs a second cold access (the delegate), so the callee can start with up to about 2,200 gas less than `callGas` (with data or with value the allowance suffices). `need` does not overflow for any `callGas` a block can supply; a `callGas` of 2^64 or more cannot be satisfied by any transaction, so `execute` reverts (with `InsufficientGas()` or an arithmetic panic; the revert data is not specified). The holder **MUST** make this check after every operation whose cost grows with the length of `data` (in particular the copy of `data` to memory, and the memory it takes) and immediately before the call. The callee therefore receives at least `callGas`.
6. Call `target` with `value`, `data` and `callGas` as the call's gas argument (when `value` is not 0, the EVM adds its 2,300 stipend). If the call fails, revert with the callee's return data (empty if the holder's balance is below `value`).
7. If `callTip` is not 0, call `msg.sender` with value `callTip`, empty data and all but one 64th of the gas that remains. If that call fails (the holder's balance, after step 6, is below `callTip`, or `msg.sender` reverts or runs out of gas), revert with `TipFailed()`.
8. Emit `Called(callNonce, target, value, keccak256(data))`, where `callNonce` is the value of `nonce` before step 4, and return the callee's return data.

Because of step 3, a holder cannot call a precompile with data directly; it can call one through an ordinary contract.

Anyone **MAY** relay a signed call and pays its gas. A signature authorises exactly one call, with one gas amount and one tip, on one chain, by one holder, at one nonce, until its deadline. A reverted `execute` changes nothing, so the same signature can be relayed again. A signature of a §5.3 message authorises the batch it names (§6.4), and is never accepted by `execute`.

The tip lets a holder pay for its own execution: anyone can put a little native coin on the holder's address, for example by withdrawing it from an exchange, and a relayer then earns the tip by submitting the signed call. A tip of 0 pays nothing. A relayer **MAY** refuse calls whose tip does not cover its gas; the holder does not guarantee that any relayer exists.

#### 6.4 `executeBatch`

`sig` is as in §6.1. `executeBatch(calls, callTip, deadline, sig)`:

1. If `block.timestamp > deadline`, revert with `Expired()`.
2. If `calls` has no element or more than 8, revert with `BadBatch()`.
3. If any `callGas_i` is at least 2^64, revert with `BadBatch()`.
4. If `sig` is not valid (§6.1) for the message of §5.3 for `calls`, `callTip`, `deadline` and `callNonce` equal to the current `nonce`, revert with `BadSignature()`.
5. Increase `nonce` by one. A batch uses exactly one nonce, whatever the number of its calls.
6. Let `need_i` be the value of §6.3 step 5 for `callGas_i` and `value_i`. If the gas left is less than Σ `need_i`, revert with `InsufficientGas()`.
7. For each call i in order:
   1. If `data_i` is not empty and `target_i` has no code at this moment, revert with `NoCode()`.
   2. If the gas left is less than `need_i`, revert with `InsufficientGas()`.
   3. Call `target_i` with `value_i`, `data_i` and `callGas_i` as the call's gas argument. If the call fails, revert with `BatchCallFailed(i − 1, returnData)`, where i − 1 is the zero-based position of the call and `returnData` is the first 256 bytes of the callee's revert data, or all of it if it is shorter (empty if the holder's balance is below `value_i`).
8. If `callTip` is not 0, call `msg.sender` with value `callTip`, empty data and all but one 64th of the gas that remains. If that call fails, revert with `TipFailed()`.
9. For each call i in order, emit `Called(callNonce, target_i, value_i, keccak256(data_i))`, where `callNonce` is the value of `nonce` before step 5. Return nothing.

The holder **MUST** make the check of step 6 after the copy of every `data_i` to memory, and the check of step 7.2 after every operation whose cost grows with the length of `data_i` and immediately before the call, as in §6.3 step 5. Step 6 is a lower bound that a relayer can compute from the signed values alone; step 7.2 is what guarantees each callee at least `callGas_i`. Neither step reserves gas for the holder's own work between calls, for the tip or for the events: a relayer that supplies too little for those pays for a transaction that reverts. The holder **MUST NOT** copy the return data of a call that succeeds (the calls of step 7 and the tip of step 8), and **MUST NOT** copy more than 256 bytes of the revert data of a call that fails, so that its own work does not depend on how much data a callee returns. A client that needs the callees' results **MAY** simulate the batch with `eth_call` and read them from the call trace.

A batch is all or nothing. If any step reverts, nothing the batch did remains, the nonce is not used, and the same signature can be relayed again until its deadline. In particular, a call that fails undoes every earlier call of the batch, and no tip is paid.

Anyone **MAY** relay a signed batch. A signature of a §5.3 message authorises exactly that list of calls, in that order, with those gas amounts and that one tip, on one chain, by one holder, at one nonce, until its deadline, and is never accepted by `execute` or `isValidSignature`. `execute` and `executeBatch` draw on the same nonce, so signing and relaying any call or batch at a nonce cancels every other signed call or batch at that nonce. The tip of a batch is paid once, after all its calls, to `msg.sender`, as in §6.3 step 7.

A batch of K calls emits K `Called` events with the same `nonce`. They are contiguous in the transaction's log, in call order, and come after any event emitted during the calls, including the events of a call or batch that re-entered the holder with the next nonce. An indexer **MUST NOT** assume that `nonce` identifies one event; it orders the holder's calls by `nonce` and then by log position, and reads the `executeBatch` calldata, or the call trace, to know which events came from one batch.

### 7. Use with TAP-11

To authorise a service signer for a circuit it holds, the holder's Bitcoin key signs the message of §5.1 for the TAP-11 §4.1 delegation digest, and the manifest's `delegation.sig` is the resulting `sig` (§6.1) as 0x-hex. TAP-11 §4.4 item 2 requires the holder to have code at the pinned block of the resolution, so a delegation by a holder that is not yet deployed is rejected: deploy it first (§4). A TAP-11 client needs no change, but one that declines EIP-1271 (TAP-11 §4.4 allows it) rejects such delegations.

Through `execute`, the holder, as the circuit's owner, can also act for the circuit's container (ERC-6551) and transfer the circuit. It cannot publish TapeSend keys: TAP-10 §13.5 rejects contract holders.

### 8. Wallets and user interfaces

A user interface that asks a user to sign a message of §5.2 **MUST** show the target, the value and the tip converted to the chain's coin, the deadline as a date and time, and the whole `data` in hex, and **SHOULD** show next to them the decoded function and its arguments where it knows the ABI; it **MUST NOT** present a call that it cannot decode as harmless, and **SHOULD** warn when the deadline is far away, since the signature stays valid until then. It **MUST NOT** ask a user to sign a message whose text differs from the text that the holder's `callMessage` or `batchMessage` returns for the call shown, or a §5.2 message with a `callGas` of 2^64 or more, which no relayer can satisfy (§6.3 step 5). A client **MUST NOT** show or use the holder address of a scriptPubKey that the constructor rejects (§3.1), because anything sent to such an address is lost. A user interface that asks for a message of §5.1 **SHOULD** show what the digest stands for (for example the TAP-11 delegation's container, signer and expiry), because the message itself shows only the digest, and **SHOULD** say that the holder cannot revoke the signature afterwards (Security Considerations, Replay). When the holder is already deployed, an interface **SHOULD** read the holder's own `callMessage(...)` or `signMessage(...)` with the same arguments through `eth_call` and compare it byte for byte with the text it is about to ask the wallet to sign; this costs nothing and catches a mistake in the interface's own encoding; it does not help against a compromised interface or a lying RPC node, which can return the text the interface expects. For a P2WPKH address an interface cannot tell whether the 20 bytes are the hash of a valid compressed public key, and for a P2TR address it cannot tell whether a key-path signature can exist at all (a taproot output may be spendable only through script paths), so it **SHOULD** say so to the user: a holder whose scriptPubKey is not usable that way can never accept a signature (Rationale). An interface **MUST NOT** state or imply that a circuit held in a holder is protected from upgrades of TapeOut's contracts (Security Considerations). An interface **MUST NOT** describe a holder, or anything a holder holds, as quantum-resistant or as protected against quantum computers (Security Considerations, Quantum computers).

A user interface that asks a user to sign a message of §5.3 **MUST** build the text from the calls it shows, **MUST** show every call as above for §5.2 (target, value, the whole `data`, and the decoded function where known), numbered as in the message, together with the number of calls, the tip converted to the chain's coin and the deadline, and **SHOULD** read the deployed holder's `batchMessage(...)` through `eth_call` and compare it byte for byte with the text before asking the wallet. It **SHOULD** say plainly that the calls happen together or not at all. It **MUST NOT** ask a user to sign a §5.3 message for a batch that `executeBatch` refuses whatever the state (steps 2 and 3 of §6.4: no call, more than 8 calls, or a `callGas_i` of 2^64 or more), although `batchMessage` renders the text of a batch with such a `callGas_i`. It **SHOULD NOT** offer a batch to a wallet or signing device whose display of the message is known to truncate it or to fall back to showing a hash.

A user interface **MUST** ask the wallet for a BIP-322 "simple" signature explicitly, with the wallet's own parameter for it (for example `signMessage(message, "bip322-simple")` of UniSat and OKX Wallet; Test Cases give the parameters of the four wallets tested, and the wallet's documentation prevails); a wallet called without one may return a 65-byte BIP-137 signature (§6.1; one did). It **MUST** request signatures only from the P2TR or P2WPKH address whose holder it shows (§2): a wallet's payment address may be P2SH-wrapped, and a wallet may sign for such an address with a witness-only signature that is valid for the P2SH-P2WPKH script (a different script, hence a different digest) and not for any supported address (one did). An interface **MUST** request the simple format through the wallet's message-signing call, and **MUST NOT** use a PSBT-based or full-format signing flow for these messages. It **MUST** ask for one message per wallet request and **MUST NOT** use a wallet call that signs several messages in one approval (for example UniSat's `multiSignMessage`): each message authorises a transfer, and a wallet may let the user approve all of them with one click without showing each. A §5.3 batch is the way to authorise several calls with one signature. Wallets show the text of a message in different ways: some show it in full, some show one line until the user opens it, some show it only behind a link, and some cut long hex fields off at the edge of the window (Test Cases). An interface therefore **MUST NOT** rely on the wallet's window for the user's understanding of a §5.2 or §5.3 message: the decoded call that the interface shows is what the user is asked to approve, and the interface **SHOULD** tell the user where the wallet shows the full text so that the user can compare the two.

## Rationale

**A contract, not a change to TAP-11.** TAP-11 §4.4 already accepts EIP-1271 holders. A contract also gives the Bitcoin key everything else a holder can do (transfer the circuit, act through its container) without asking the circuit contracts, the hub or any client to change.

**BIP-322, not bare BIP-340.** None of the four wallets tested (Test Cases) offers a signature of an arbitrary 32 bytes with BIP-340 to a web page; they sign text messages with BIP-322, as does Sparrow's signing library (the Sparrow application itself was not tested). A bare-BIP-340 path would add a signature form only custom software could produce. The digest of a simple signature is a BIP-143 or BIP-341 signature hash of a virtual transaction, structurally different from the digests of BIP-137 message signing (which begins with the 0x18 byte and `Bitcoin Signed Message:`), Nostr events and Lightning messages, so equal digests across protocols would be a SHA-256 collision. Related designs that verify Bitcoin message signatures on other chains: CKB's Omnilock (RFC 42, P2TR not supported) and NEAR Intents (BIP-322 payloads inside a verifier contract).

**Messages that name the holder and the chain.** BIP-322 signs text. A message that were only the digest would be valid wherever the same text is accepted, including other holders and other chains. Naming the holder and the chain makes every signature valid for one holder on one chain; it also tells the user which account is acting, though not what an opaque digest means (§8).

**The call's gas is signed.** Without it, a relayer could choose how much gas the call receives; a target that does not revert when an inner step runs out of gas would then do less than the user meant while the nonce is still used. Signing `callGas` and checking that the relayer supplies it (the same rule as a Safe's `safeTxGas`) leaves the relayer no choice. A security review of an earlier version of this draft found this and the two checks below; all three were adopted before the creation code was fixed.

**Calls with data to an address without code are refused, and P2TR keys are checked at deployment.** A call with data to an address that has no code succeeds without doing anything, which hides a wrong address or a target missing on that chain; `NoCode()` makes it fail. A P2TR output key that is not usable for BIP-340 would make a holder that accepts no signature, so that anything sent to it is lost; the constructor refuses such keys. A holder address for such a key is never deployed, so tokens sent to it stay unrecoverable: an interface checks a key before showing its holder address (§8). A P2WPKH key hash cannot be checked at deployment; a hash that is not that of a compressed key gives a holder that accepts nothing.

**The tip is signed and paid to `msg.sender`.** Without a way to pay for execution, a holder's owner would need an EVM account with coin in it, which is what this TAP is meant to avoid. A signed tip is the smallest mechanism that fixes this: the holder's own balance pays whoever submits the call, nothing depends on a gas price, and a relayer needs no registration. It is deliberately not an ERC-4337 account (which needs a bundler network, an entry point and a deposit), not payable in tokens, and not addressed to a named relayer; those are possible later versions. The tip is paid after the call, so a failed call pays nothing, and a tip that cannot be paid undoes the call.

**A separate message for calls.** If calls were authorised by signing a digest, a site could present a call's digest as, say, a delegation, and the user could not tell. The call message spells out the target, value, data hash, gas, tip, nonce and deadline, and cannot be confused with a §5.1 message, which always contains ` signs `, or with a §5.3 message, which continues with ` makes `.

**Batches in the same contract.** A batch lets one signature, and one wallet prompt, cover steps that belong together (claim a reward, then move it; move a circuit, then delegate), without signing at nonces n, n+1, n+2 in advance, where the later signatures wait for an earlier call that fails. It is part of this contract rather than a later version because a later version would need new creation code, and so a second holder address for the same Bitcoin address. Measured on a local node, a batch of 8 ERC-721 transfers costs about 58% less gas than 8 separate calls (Measured cost, below).

**The batch message lists every call.** A single hash of the list would keep the message short, but the user would see nothing but a hash, which is the argument against digests above. The batch message shows each call's target, value, gas and data hash, as §5.2 does, and adds only the count and the numbering.

**All or nothing.** The calls a user groups usually depend on one another. If a later call ran after an earlier one failed, the outcome would be one the user did not sign, and the nonce would be used anyway; per-call results would also need a rule for the tip of a partly failed batch. With all or nothing, a batch either does what its text says or does nothing, which is the guarantee `execute` gives for one call. A user who wants independent calls signs separate messages. `BatchCallFailed` names the failed call so that an interface can tell the user which one it was, and carries the first 256 bytes of its revert data, which hold the error selector and its usual arguments; a callee that reverts with more cannot make the holder spend more on the error. `execute` keeps returning the callee's revert data unchanged.

**The gas of a batch.** Each call keeps its own signed `callGas` and the check of §6.3 before it. The up-front check of the sum makes a relayer that cannot cover the signed total fail before any callee runs. Because the holder never copies a callee's return data and copies at most 256 bytes of revert data, its own work depends on the signed values and the call data only, not on what the callees return; so the gas a relayer must supply follows from what it relays, whatever the callees do within their `callGas`. For the same reason `executeBatch` returns nothing: returning each callee's data would make the holder copy and keep all of it, at a cost that grows with the square of its total size. The 2^64 cap keeps the sum from overflowing and is far above any block gas limit. The code check is made before each call, not up front, so that a call may create the target of a later one (for example, call 1 deploys an ERC-6551 account and call 2 uses it); since a batch is all or nothing, checking later loses nothing.

**At most 8 calls, one `Called` per call.** The limit bounds the text a user has to read (about 1,300 bytes for 8 typical calls, at most about 2,240 for a chain ID of at most 20 digits) and the work of one transaction; more calls would add little, since the saving against separate calls is 58% at 8 calls and is estimated not to exceed about 69% however many calls a batch has. Existing indexers of `Called` see every call of a batch without change, and emitting the events together after the tip, as `execute` does, keeps one batch's events contiguous.

**Deterministic address with fixed bytes.** One Bitcoin address must lead to one holder, whoever deploys it and on whichever chain. That needs the same init code everywhere, hence the fixed creation code and compiler settings. The deterministic deployment proxy exists with the same 69 bytes of code on BNB Smart Chain, Base and X Layer (read on 2026-10-08).

**Relation to ERC-7913.** ERC-7913 (Final) lets an account accept signatures by a key that has no address through a stateless verifier contract. The verification code of §6 could be offered as such a verifier, and a later TAP can do that. It is not what this TAP defines, because the holder has to be the contract that holds the assets and makes the calls, and a verifier can do neither.

**The `ecrecover` construction.** BIP-340 verification in plain Solidity costs about a million gas (a pure-Solidity secp256k1 library measured in the prototype; informative). With `ecrecover` it costs a few thousand: setting the recovery inputs to (−s·x(P), x(P), −e·x(P)) recovers the address of s·G − e·P, which is compared with the address of the even-y point lifted from r. The use of `ecrecover` for Schnorr verification was described in 2018 (Vitalik Buterin, ethresear.ch) and is implemented, with the same rejection of x ≥ n and e = 0, in Blockstream Research's `ecrecover-schnorr-verifier`; what is specific to this TAP is the BIP-322 and BIP-341 signature hash reconstruction around it. The comparison is between 160-bit hashes of points: a forgery needs a second preimage of a 160-bit hash, the work that an attack on an Ethereum address needs. It rejects keys with x ≥ n and challenges e = 0, which occur with probability below 2^-127.

**Measured cost** (informative; reference implementation, transaction receipts on a local node with BNB Smart Chain's chain ID and the `shanghai` rules, 2026-10-10; the numbers are in `assets/tap-draft-bitcoin-keyed-holders/docs/FINAL-GAS.md`): deploying a holder about 1,604,000 gas; `isValidSignature` sent as a transaction about 37,900 gas for P2TR and 40,500 or 43,800 for P2WPKH (one or two `ecrecover` calls, depending on the signature), of which an EIP-1271 verifier contract pays about 15,200 for P2TR and at most about 20,600 for P2WPKH inside its own call; `execute` of an ERC-721 transfer about 95,000 gas (78,000 when the holder's nonce is not 0) and 103,000 with a tip; `executeBatch` of 2, 4 and 8 such transfers about 123,000, 173,000 and 267,000 gas, against 173,000, 329,000 and 636,000 for as many separate `execute` calls (P2TR; a P2WPKH signature check costs up to about 3,300 more).

**Alternatives considered.**
- *Only two address kinds.* The BIP-322 "simple" format carries only a witness stack; the `to_sign` input's scriptSig is empty, and the BIP gives scriptSig data only to the *full* format, for outputs that are not native segwit. A P2SH-wrapped segwit address, such as the payment address of some wallets, therefore cannot be expressed in the simple format. Supporting full signatures and P2PKH would add a second signature format with more parsing, and P2WSH, taproot script paths and multisig would add script evaluation; each can be a later version.
- *ERC-4337 accounts.* They would add gas sponsorship but need a bundler network, an entry point and a deposit; the signed tip (above) covers the common case with one contract.
- *EIP-7702.* It lets an EVM externally owned account delegate to code, but a person who has only a Bitcoin key has no EVM account to delegate from.
- *A shared factory or registry.* The deterministic deployment proxy makes the holder address computable without a registry, and keeps the TAP free of a contract that someone would have to own.
- *Recovery.* Social recovery, time locks and a second key were left out because each is a second authority; a later version can add them with new creation code.
- *Per-call results in a batch, a digest of the calls, or a compact calldata encoding.* The first two are discussed above. A compact encoding of `execute` saves about 1% of the total fee on an OP Stack chain at the L1 data prices of 2026-10-10, which does not justify a second encoding for every relayer and indexer to implement.

**What it does not do.** It moves no bitcoin and verifies nothing on the Bitcoin chain. It is not a bridge. Losing the Bitcoin key loses the holder's assets for good, as with any self-custody key, and the contract has no recovery by design: any recovery path would be a second authority.

**Why Application, and what the editors are asked.** The draft adds a convention on top of TAP-11 and changes no requirement of TAP-10 or TAP-11: a client that does not know it loses nothing. TAP-01 §3 lists contract interfaces and client verification rules under Standards, and this draft fixes a contract byte for byte and defines three message formats, so the editors may rule that it is a Standards TAP; it then needs the Reference Implementation at a fixed commit before Review, which the draft already says. The holder contract itself has no upgrade path and depends on no other contract. What it is for, however, depends on TapeOut contracts that others can upgrade (Security Considerations), so under TAP-01 §5.1 this TAP goes through Candidate before Final and cannot become Final until those contracts are sealed.

## Backwards Compatibility

Nothing existing changes. A later incompatible version needs new creation code, which gives every Bitcoin address a new holder address; holders of this version keep working. The author is testing such a candidate (the two EIP-7702 cases of §6.3 step 3 and step 5, the draft form of EIP-1271 described next, and a hash-based recovery key that does not enter the holder address); if it is adopted, it will replace the creation code of §3.2 in this draft before Review, while no holder is in use, rather than become a second version. A consumer that still calls the draft form of EIP-1271, `isValidSignature(bytes,bytes)` (selector `0x20c13b0b`), cannot use a holder: Safe v1.4.1 and earlier call that form on a contract owner, while v1.5.0 calls the final `isValidSignature(bytes32,bytes)` that a holder implements.

The compiler, solc 0.8.28 with the Yul optimizer, is within the range of the reported optimizer bug SOL-2026-7 (fixed in a later release); the shipped bytes were compared by differential testing with a build with the Yul optimizer off (20,000 runs for each of `signMessage`, `callMessage` and `batchMessage` with extreme values, and for `execute` and `executeBatch`): no divergence. `assets/tap-draft-bitcoin-keyed-holders/tools/` (MIT, dependency-free Python, plus `assets/tap-draft-bitcoin-keyed-holders/tools/wallet-lib-check/`, a JavaScript signer check pinned to exact package versions): secp256k1, BIP-340, RFC 6979 ECDSA, bech32/bech32m, BIP-322 signing and verification, holder addresses and messages (including the batch message and its parser), and the vector generators; it reproduces all upstream vectors. The tests need Foundry and forge-std v1.17.0 (`forge install foundry-rs/forge-std@v1.17.0` in `assets/tap-draft-bitcoin-keyed-holders/contracts/`). `assets/tap-draft-bitcoin-keyed-holders/scripts/demo_fork.sh`, `assets/tap-draft-bitcoin-keyed-holders/scripts/mining/demo_mining.sh` and the logs under `assets/tap-draft-bitcoin-keyed-holders/scripts/logs/` show the flows on local forks of BNB Smart Chain, Base and X Layer. ## Deployments

This TAP deploys no shared contract. Holders are deployed on demand through the deterministic deployment proxy `0x4e59b44847b379578588920cA78FbF26c0B4956C`, whose runtime code is the same 69 bytes on BNB Smart Chain (56), Base (8453) and X Layer (196), `keccak256` `0x2fa86add0aed31f33a762c9d88e807c475bd51d0f52bd0955754b2608f7e4989` (`eth_getCode`, 2026-10-08). Anyone can check a holder by recomputing its address (§4) and comparing its runtime code with the reference build. The circuits that a holder is meant to hold are not deployed by this TAP, and their contracts are upgradeable (Security Considerations).

## Security Considerations

- **The Bitcoin key is the only authority over the holder.** Whoever has it controls every asset of the holder on every chain, subject to the contracts that hold or issue those assets (below); whoever loses it loses them. There is no recovery and no second key.
- **What users see.** A §5.1 message shows the holder, the chain and a digest, but not what the digest means. A §5.2 message shows the target, the value in the smallest unit and the nonce, but only a hash of the call data, so a call that approves an operator for every token looks the same as a harmless one. A malicious interface can therefore have a user sign any call; the user's only protection is the interface that asks for the signature (§8), as with any wallet that signs hashes. The message carries no domain (it is the same text on every site), so a wallet cannot bind it to the requesting site; relayers need origin-independent signatures, and a phishing page can request byte-identical text.
- **Batches.** A §5.3 message makes this worse: an approval of every token can sit among seven harmless transfers, and long texts are skimmed. The count at the start and the numbering let a user check that the wallet shows the whole text, but not what each call does; the only real protection is the interface's decoding (§8), and a batch request from an unknown site deserves the care of as many separate requests. Calls that are harmless one at a time can be harmful together, for example an approval of an operator followed by a call that lets the operator act, in one step that nobody can interrupt. No wallet limit on the length of a BIP-322 message is documented; four wallets signed texts of 2,239 characters and three of them (Xverse, Leather and OKX Wallet) a text of 4,000 characters, but hardware signers are untested. A wallet or device that cuts the text off, or shows a hash instead, would hide later calls. A relayer cannot reorder, drop, add or partly execute the calls of a batch; it relays the whole batch or nothing.
- **Replay.** Every message names the holder and the chain, so a signature is valid for one holder on one chain. A call signature is also bound to one nonce and a deadline. A §5.1 signature has no expiry of its own: it is valid for as long as the digest is, and the meaning of the digest (for example a TAP-11 delegation's `expires`) decides that. **The holder has no way to revoke a §5.1 signature.** Once the key has signed, every EIP-1271 consumer on that chain accepts it for as long as the consumer accepts the digest; spending nonces, emptying the holder or signing anything else does not invalidate it (tested). The only revocation is the consumer's own (a TAP-11 delegation's expiry, a marketplace's cancel call), so §8 asks an interface to say this before it asks for a §5.1 signature. If a circuit leaves a holder and returns before a delegation expires, the old signature is valid for it again. Two chains that share a chain id (after a contentious fork) accept the same signature while their nonces agree.
- **Bitcoin transactions.** A BIP-322 simple signature is a signature over the signature hash of a virtual transaction (`to_sign`): one input that spends output 0 of `to_spend` with an amount of 0, one output of value 0 with the script `OP_RETURN`, version 0, lock time 0 and sequence 0 (BIP-143 for P2WPKH, BIP-341 for P2TR; both commit to the amount). A real spend commits to another amount, other outputs, or another version, lock time or sequence, and `to_spend` has a null previous output and a script that does not begin with a BIP-34 height push, so no block above height 0 can confirm it and no output has its txid. These properties hold whatever the message text is, unless SHA-256 collision resistance is broken (about 2^128 work for an attacker who chooses the message, the same bound as for any message signing, BIP-137 included). They hold for the simple format only: the full and proof-of-funds formats and PSBT-based signing add inputs and signature hash types that the requester chooses, which is why §8 requires the simple format through the wallet's message-signing call. Under Bitcoin's own assumptions signing puts no bitcoin at risk; on the EVM side it authorises whatever the message says.
- **Relayers.** A relayer chooses when to submit a signed call, within its deadline, and pays the gas; it cannot change the call, and it cannot change the gas the call receives except in the EIP-7702 case of §6.3 step 5. Users who need a call to happen soon should choose a short deadline; cancelling a signed call is best effort: a user can sign and relay another call at the same nonce first, but whoever already holds the original signature can relay it first, and then the cancel fails with `BadSignature()`; a short deadline is the real control. A cancel can be `execute(<any externally owned account without an EIP-7702 delegation>, 0, "", 0, 0, deadline, sig)` (value, data, `callGas` and tip all 0); a self-call with `callGas` 0 always fails, because `receive()` then gets no gas. A `callGas` that is too low makes the call fail and the whole `execute` revert, without using the nonce.
- **Holders that are not yet deployed, and addresses that cannot be used.** Tokens sent to an undeployed holder address are held by the Bitcoin key once the holder is deployed, and until then nothing can move them; TAP-11 delegations and `execute` do nothing until someone deploys it (§7). The address is only meaningful on a chain where the proxy exists and the creation code deploys (§4 item 4); assets sent to it elsewhere are stranded. A P2TR address passes the constructor check whenever its output key is on the curve, even if no key-path signature can exist (a script-only output or an unspendable key); assets sent to the holder of such an address can never move. A P2TR output that commits to a script tree can be signed only with the key that includes the tree's tweak, which BIP-86 wallets do not use; when a third party (an exchange, a custodian) holds the key-path key, that party controls the holder. Threshold outputs (MuSig2, FROST) work only if the group can produce a key-path BIP-322 simple signature; none of the wallets reviewed (UniSat, Xverse, Leather, OKX Wallet) offers it. Different address kinds, even of one wallet, give different holders (P2WPKH and P2TR), and other kinds give none; an interface shows the holder of the address that will sign.
- **Contracts reached through TAP-11.** The DeWEB hub (`0xe61A9C7213a6Aa616C246a2B569e555B417b25ee`, the same address on BNB Smart Chain, Base and X Layer; read on 2026-10-12) is upgradeable by a single key (`0x571d447f4f24688ec35ccf07f1d6993655f6af15`), not by the Safe below; that key is also one of the Safe's five signers. This was read by simulating the upgrade call from that key and from another address; the authorisation source of the contract was not read. The SiteRegistry and the DomainBinding are upgradeable by another single key (`0xe4fc10592fa8ad7c408b81e99cfc54ef4b14283d`). Whatever a holder does through TAP-11 services is only as safe as these contracts; the Bitcoin key gives no protection against their upgrade.
- **Not every TapeOut feature.** A holder cannot use TapeSend (TAP-10 §13.5). Execution on each chain is paid for by a relayer, which is repaid from the holder's own balance through the signed tip (§6.3); a holder with no native coin depends on someone else relaying for free.
- **The tip.** The tip is paid to the account that sends the transaction (`msg.sender`), not to `tx.origin`; a relayer that is a contract receives it in its `receive` (or payable fallback) function, with all the gas that remains, and may re-enter the holder, which is safe because the nonce is increased before the call. A tip is part of what the user signs, so a malicious interface can ask for a large one; the interface shows it (§8). The tip, the call's value and any coin the call itself spends all come from the holder's balance, and the whole call reverts if the balance cannot cover them. Because the tip goes to `msg.sender`, anyone who copies a relayer's pending transaction can take it; a relayer can avoid this by submitting through a private channel. The check of §6.3 step 5 does not reserve gas for the tip: a relayer that supplies too little gas pays for a transaction that reverts. Events are emitted after the tip is paid, so when the recipient re-enters `execute` the `Called` events can appear out of order; a batch also emits one `Called` per call with the same `nonce`, so an indexer cannot take `nonce` as identifying one event (§6.4). The tip of a batch is paid once; the values of all its calls, the tip and anything the calls spend come from the holder's balance, and a shortfall at any point reverts the whole batch.
- **What the wallet shows.** Of the four wallets tested, only one showed the text without the user opening anything (in a scrollable box); the others showed one line, nothing until a link was opened, or the text with the holder, target and data-hash fields cut off at the edge of the window. Each lets the user sign without having seen the call's target or data hash. The wallet's window is therefore no evidence that the user saw what a call does, which is why §8 makes the interface's decoded call the thing the user approves.
- **What a relayer pays for.** `executeBatch` copies and hashes the data of every call before it checks the signature (§6.4). A relayer whose transaction fails because the nonce was used first, for example by another signed call at the same nonce, pays for that work: about 1,030,000 gas for 8 calls of 24,000 bytes each, against about 120,000 for 8 calls without data (`assets/tap-draft-bitcoin-keyed-holders/docs/FINAL-GAS.md`, finding F-06). A relayer can avoid this by reading `nonce()` just before it sends, sending through a private channel, and asking a larger tip for batches with a lot of call data. `execute` returns the callee's return data, so its own cost grows with that data (about 1,160,000 gas for a callee that returns 200,000 bytes, against about 79,000 for none) and a callee whose return size depends on state can make an `execute` that simulated well fail on chain at the relayer's cost; a relayer that simulates against the latest state and allows a margin avoids most of this. `executeBatch` does not have this problem: it returns nothing and copies no return data.
- **Texts for batches that cannot run.** `batchMessage` renders the text of a batch with a `callGas_i` of 2^64 or more, which `executeBatch` always refuses; a signature of such a text is wasted, not dangerous. §8 forbids asking for one.
- **The gas check before a call.** The check of §6.3 step 5 and §6.4 steps 6 and 7.2 guarantees a callee its `callGas` only if nothing whose cost grows with the call data happens between the check and the call. The creation code of the earlier draft copied `data` into memory after the check, so a relayer that supplied the least gas could make the callee of a call with about 16,000 or 24,000 bytes of data receive about 1,800 or 5,200 gas less than `callGas` (measured; a candidate batch build had the same flaw, measured for a batch of one call). The current code copies all call data first, and the tests show no shortfall up to 24,000 bytes per call. A callee that does not revert when it runs out of gas is the case this matters for; a callee that reverts makes the whole call or batch revert without using the nonce.
- **Gas caps.** A chain that adopts a per-transaction gas cap of 2^24 (EIP-7825) cannot run a call whose `callGas`, or a batch whose Σ `need_i`, is above it; the user signs again with less. A relayer can warm accounts and slots with an access list so that a gas-sensitive callee runs cheaper than the user simulated; `callGas` bounds the gas, not its price.
- **Signed calls are ordered.** A call signed for nonce n+1 cannot run until nonce n is used. A call signed for nonce n that always reverts (for example, with too little `callGas`) is never executed and uses no nonce, so later signatures wait until the user signs and relays another call for nonce n; its distant deadline does not release them. §8 asks interfaces to show the deadline.
- **Consumers of EIP-1271.** The check costs about 15,000 to 21,000 gas, far more than an EOA's `ecrecover`, so a consumer that forwards a small fixed amount of gas to `isValidSignature` sees an out-of-gas failure as an invalid signature. EIP-1271 needs code at the address, and this TAP does not use ERC-6492: a consumer cannot verify the signature of an undeployed holder, so the holder has to be deployed before it signs for such a consumer.
- **Everything is accepted.** The holder accepts every ERC-721 and ERC-1155 token sent to it, so it collects unsolicited tokens, some with misleading metadata; dealing with them takes signed calls, which feed the problem of "what users see". ERC-777 `send` to a holder reverts without a registration in the ERC-1820 registry, and ERC-1363 `transferAndCall` reverts, so those tokens need a plain `transfer`.
- **Contract-only limits.** An application that requires its caller to be an externally owned account (`msg.sender == tx.origin`) cannot be used through a holder; TapeSend is one (§7).
- **Mining rigs in custody.** A rig that is deposited in a vault, or any asset held by a contract that another party can upgrade, is only as safe as that contract. The RigVault (`0x48D43345656f0f9510dC3c06CBa99dFf597617C2` on BNB Smart Chain) and the voucher (`0x9cfc959cd42B2e1d39a0d850c528210E818AE520` on X Layer) of the cross-chain scheme of 2026-10-07 are upgradeable by a 3-of-5 multisig (read from the contracts' owner on 2026-10-08), which can move any rig in custody; a holder gains no protection from the Bitcoin key against that.
- **Circuits in the custody of TapeOut's own contracts.** Who owns a circuit is recorded in contracts that a 3-of-5 Safe can upgrade. On BNB Smart Chain the beacon of the circuit processors (`0xf8D6d8EB894d6971c8976Ad8b4971cbEFE028156`) is owned by the processor factory (`0x68224F668083c29e9800Be2a646d42d18cedF7e2`), an upgradeable proxy, which is owned by the Safe `0xB3D85b42A045c1A88D800CAD0F55d2566a4D3138` (read on 2026-10-09: threshold 3 of 5, Safe version 1.4.1, no guard and no module, so an upgrade has no delay). One Safe transaction can replace the code of every circuit and change who owns it, including a circuit that a holder already holds; the Bitcoin key gives no protection against that, before or after any call of the holder. The Safe's transaction can be signed in advance and executed by anyone. This is why TAP-01 §5.1 sends a TAP that depends on upgradeable contracts through Candidate. Until the factory and the beacon are sealed, a circuit in a holder is not out of reach of the TapeOut multisig (§8 forbids an interface to say otherwise). On Base and X Layer the beacon (`0xf70d1ed4f62cf3780157b0b421b7e2f45bd0991c`, the same on both) is owned by a factory (`0x1f09DAeFA827f02CBb40967cc91b259763760761`, the same on both) that is owned by the same Safe `0xB3D85b42A045c1A88D800CAD0F55d2566a4D3138`, with the same threshold and version and no guard or module (read on 2026-10-09).
- **Rewards follow the owner at the moment of the claim.** The mining contract pays the current owner, so rewards accrued before a rig reached the holder go to the holder, and a seller can claim just before handing a rig over.
- **Privacy.** The holder address publicly links a Bitcoin address to everything the holder does on every chain. Anyone can compute the holder address of any Bitcoin address from its scriptPubKey alone (§4), before the holder is deployed and whether or not it ever is, and so can build a table from holder addresses back to Bitcoin addresses for as many Bitcoin addresses as they like. A Bitcoin address used only for signing holder messages (Quantum computers, below) keeps the holder apart from the user's other Bitcoin addresses and their bitcoin, but not from that signing address.
- **Signature strength.** The P2TR path compares 160-bit addresses of points instead of points (Rationale), as Ethereum's own signatures do; the P2WPKH path uses `ecrecover` directly. An ECDSA signature whose nonce point has an x-coordinate of n or more cannot be represented to `ecrecover` and is refused although it is valid; a signer meets this with probability about 2^-128.
- **Quantum computers.** Every authority over a holder is a secp256k1 key (BIP-340 for P2TR, ECDSA for P2WPKH). Nothing in this TAP resists an attacker who can compute a private key from its public key: such an attacker can sign any message of §5 for the holder, on every chain. Only the derivation of the holder address (§4) relies on hashes alone, and that says nothing about who controls the holder. When the key becomes public depends on the address kind. A P2TR output key is the 32 bytes that follow `0x51 0x20` in the scriptPubKey (§2), so it is public from the start, in the Bitcoin address itself and in the holder's init code (§4 item 1). A P2WPKH scriptPubKey holds only the hash of the key; the key is in the witness of every simple signature (§6.1), so it becomes public with the first signature that is published: in the calldata of `execute` or `executeBatch`, in a TAP-11 manifest's `delegation.sig` (§7), or wherever else the signature appears; any Bitcoin transaction that spends from the address publishes it too. A holder has one address on every chain, so one exposure covers all chains, and a key that has been public stays public. A user who wants to delay the exposure should use a P2WPKH address dedicated to the holder, used only to sign holder messages and never funded with bitcoin. This changes when the key becomes public, not whether: after its first published signature such a holder is as exposed as a P2TR holder, and a holder of this version cannot change its key, add a second key or stop accepting signatures. The only response it allows is to move assets, with a signed call made while the key is still safe, to the holder of another Bitcoin address whose key is not yet public. §8 forbids an interface to describe a holder as quantum-resistant. Options for a later version with a hash-based recovery key are being evaluated; this draft commits to none of them, and any such version needs new creation code and therefore gives every Bitcoin address a new holder address (Backwards Compatibility).
