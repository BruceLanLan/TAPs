# TAP-02：电路网表格式与求值语义

## 概要

本 TAP 逐字节写明 TapeOut 电路在链上如何存储、计算什么，让任何人都能写出与链上结果一致的编译器、模拟器和验证工具。

## 摘要

TapeOut 上每个流片的电路都是一份网表：由处理器合约保存的一串 NAND、LATCH、REF 记录。本 TAP 规定：记录的编码、信号的编号、网表合法的条件、输入/输出/状态的位打包方式，以及一拍求值的结果（包括 LATCH 反馈和 REF 子电路）。本 TAP 同时列出读取网表和求值结果的只读合约函数，并附测试向量、参考实现，以及与 BNB Smart Chain 主网上 24 个电路的对比结果。

## 动机

网表格式是协议的核心：画布、求值器、设计证明（PoD）审查、第三方工具和 V2 元件都依赖它。目前它只由官方前端和合约的代码定义。独立工具只能从这些代码反推格式，实现者也无从知道哪些细节有保证，哪些只是某个实现的偶然行为。

没有成文标准时：

- 编译器（例如 Verilog 到 TapeOut）无法知道链上接受哪些网表；
- 验证工具说不清自己证明了什么，因为"等价"取决于求值语义，特别是 LATCH 的时序和 REF 的状态；
- 其他 TAP（例如元件互联标准或数据格式类 TAP）没有关于位序和信号编号的规范可以引用。

## 规范

本文中的关键词"MUST"（必须）、"MUST NOT"（不得）、"REQUIRED"、"SHALL"、"SHALL NOT"、"SHOULD"（应当）、"SHOULD NOT"（不应）、"RECOMMENDED"、"NOT RECOMMENDED"、"MAY"（可以）和"OPTIONAL"，当且仅当以全大写出现时，按 RFC 2119 和 RFC 8174 解释。

编码（§2）、状态排布与一拍语义（§4）、位打包（§5）以及 §6 中的只读函数，已于 2026-09-29 在 BNB Smart Chain 主网上得到确认（见"测试用例"）。合法性规则（§3）、填充位与字节长度的处理（§5）以及 `tapeout` 的检查（§6），依据电路实现 `0x8E1D125Def6d3826C278299273a0760D47626068` 的已验证源码（`Circuits.sol` 和 `lib/NetlistVM.sol`，MIT 许可，已在 BscScan 验证），于 2026-09-30 阅读。唯一标有 **[待定]** 的一项列在"安全考虑"末尾的"待定问题"中。

### 1. 术语

| 术语 | 含义 |
|---|---|
| 处理器合约 | 由处理器工厂创建的 ERC-721 合约，负责保存和求值电路。合约接口中称为 "cpu" |
| 电路 | 一个二元组（处理器合约，电路编号）。每个处理器合约内电路编号从 1 开始 |
| 网表 | 定义一个电路的记录字节串，连同 `nIn` 和 `nOut` |
| 信号 | 一个比特值，以编号标识 |
| 元素 | 一条解码后的记录 |
| 一拍 | 一次求值：从（状态，输入）到（新状态，输出） |

### 2. 信号与记录

一个电路有 `nIn` 个输入、`nOut` 个输出，`0 ≤ nIn ≤ 65,536`，`1 ≤ nOut ≤ 65,536`。`nIn` 可以为 0（电路只由自身状态驱动）。信号编号如下：

| 编号 | 信号 |
|---|---|
| 0 | 常数 0 |
| 1 | 常数 1 |
| 2 … 2 + nIn − 1 | 各输入，第 `i` 个输入的编号为 `2 + i` |
| 2 + nIn 起 | 各元素的输出，按记录顺序；每个元素依次追加自己产生的信号 |

网表就是记录的直接拼接，没有文件头、填充或结束标记。`nIn` 和 `nOut` 不属于网表字节，与网表分开保存（§6）。所有多字节整数均为大端序。`u24` 是 3 字节无符号整数，用于信号编号。

| 操作码 | 名称 | 操作码之后的记录内容 | 记录长度 | 产生的信号 |
|---|---|---|---|---|
| `0x00` | NAND | `a:u24 b:u24` | 7 字节 | 1 个：`NOT (a AND b)` |
| `0x01` | LATCH | `d:u24` | 4 字节 | 1 个：保存的状态位（§4） |
| `0x02` | REF | `cpu:20 字节, id:u64, nIns:u8, nOuts:u8, ins:u24 × nIns` | 31 + 3·nIns 字节 | nOuts 个：电路（`cpu`, `id`）的输出 |

### 3. 合法性

参数为 `nIn`、`nOut` 的网表合法，当且仅当下列条件全部成立。记 `S` 为信号总数：`2 + nIn` 加上所有元素产生的信号数。

1. 每个操作码都是 `0x00`、`0x01` 或 `0x02`，且最后一条记录完整；
2. `nIn ≤ 65,536`，且 `1 ≤ nOut ≤ 65,536`；
3. 元素产生的信号至少有 `nOut` 个，即 `2 + nIn + nOut ≤ S`。因此输出总是由元素产生的信号，永远不会是输入或常数；
4. NAND 的每个输入 `a`、`b`，以及 REF 的 `ins` 中每一项，其编号都**小于**该元素产生的第一个信号的编号（只能向前引用）；
5. LATCH 的 `d` 可以是小于 `S` 的任意编号（可以向后引用，这是构造反馈的唯一方式）；
6. 对 REF：`cpu` 是在处理器工厂登记过的处理器合约（`isCPU(cpu)` 为真）；电路（`cpu`, `id`）存在；其 `nIn` 等于 `nIns`、`nOut` 等于 `nOuts`（因此只能引用输入、输出各不超过 255 个的电路）；其 `nState` 不超过 2^24；
7. 包括 REF 子电路在内，状态总位数不超过 2^24，门总数不超过 2^32 − 1；
8. `S ≤ 2^24`。`tapeout` 不直接检查这一条，但这么大的网表放不进一笔交易；工具仍然必须拒绝。

工具必须拒绝不合法的网表，也不得生成不合法的网表。`tapeout` 检查第 1–7 条（`Circuits.tapeout` 和 `NetlistVM.analyze`），按记录顺序检查，遇到第一处不合法即回滚。回滚原因如下：

| 条件 | 回滚原因 |
|---|---|
| 1 | `bad opcode`；记录不完整时，以 Solidity panic `0x32`（数组越界）回滚，没有原因字符串 |
| 2 | `no outputs`（nOut = 0）；`too many pins`（nIn 或 nOut 超过 65,536） |
| 3 | `too few signals for outputs` |
| 4 | `NAND: future signal`；`REF: future signal` |
| 5 | `LATCH d out of range` |
| 6 | `REF: target not a registered CPU`；`no circuit`（来自目标电路的 `circuitInfo`）；`REF: pin mismatch`；`REF size` |
| 7 | `size overflow` |
`tapeout` 不限制 REF 嵌套深度，网表长度也只受交易 gas 限制。（`NetlistVM` 里"最多 16 层 REF"的限制只用于设计证明（PoD）挖矿计算关键路径深度，与流片无关。）

由于 REF 只能引用在当前电路流片时已经存在的电路，而已保存的电路没有任何修改接口，REF 引用关系不会形成环。处理器合约是信标代理（见"部署"），所以只有在信标背后的电路实现不变时，这一点才成立 **[待定：直到工厂封存为止]**。

### 4. 状态与一拍

**状态排布。** 电路的状态是长度为 `nState` 的位向量。按记录顺序遍历元素：每个 LATCH 分到下一个状态位；每个 REF 分到接下来的 `nState(sub)` 位，其中 `sub` 是被引用的电路。`nState` 是总位数。一个电路（直接或通过 REF）没有任何 LATCH 时，`nState = 0`，是组合电路。

**一拍**的输入是 `state`（长度 `nState`）和 `inputs`（长度 `nIn`），输出是 `newState` 和 `outputs`：

1. 令信号 0 为 0，信号 1 为 1，信号 `2 + i` 为 `inputs[i]`；
2. 按记录顺序处理每个元素：
   - NAND：输出为 `1 − (s[a] AND s[b])`；
   - LATCH：输出为它在 **`state` 中**的状态位（上一拍保存的值）；
   - REF：用它在 `state` 中的那一段状态、以 `s[ins[0]] … s[ins[nIns − 1]]` 为输入，对被引用电路求值一拍；该拍的输出即 REF 的输出，该拍的新状态即 REF 在 `newState` 中的那一段；
3. 所有元素处理完之后，每个 LATCH 在 `newState` 中的位等于 `s[d]`，即本拍中 `d` 的值；
4. `outputs` 为最后 `nOut` 个信号，即 `s[S − nOut] … s[S − 1]`，按编号顺序。

因此，LATCH 在某一拍的输出永远不依赖该拍的输入；LATCH 就是一拍的延迟。

### 5. 位打包

输入、输出和状态以字节串与合约交换。向量的第 `i` 位是第 `floor(i / 8)` 字节的第 `i mod 8` 位（值为 `2^(i mod 8)`）：低位在前。

- **输出和新状态**：恰好 `ceil(n / 8)` 字节，最后一个字节中未使用的高位为 0。
- **传给 `eval` 和 `step` 的输入和状态**：宽松读取。第 `i` 位所在的字节超出字节串末尾时按 0 读；超过 `n` 的位和字节一律忽略。合约从不因为长度或填充位拒绝输入或状态。调用方应当发送恰好 `ceil(n / 8)` 字节、填充位为 0；符合本 TAP 的求值器必须按与合约相同的方式读取其他长度的字节串。

### 6. 合约接口（只读部分）

处理器合约至少提供：

| 函数 | 选择器 | 返回 |
|---|---|---|
| `nextId()` | `0x61b8ce8c` | 下一个流片电路将得到的编号 |
| `circuitInfo(uint256 id)` | `0x084d60f1` | `(uint32 nIn, uint32 nOut, uint32 nState, uint32 gateCount)`。`gateCount` 统计所有 NAND 和 LATCH，包括通过 REF 引用进来的；不含 REF 的电路等于自身的 NAND + LATCH 记录数。编号不存在时回滚 `no circuit` |
| `netlist(uint256 id)` | `0x3fc4be56` | `bytes`：完全按 §2 编码的网表 |
| `eval(uint256 id, bytes inputs)` | `0x934d06ea` | `bytes`：一拍的输出（已打包）。对 `nState > 0` 的电路会回滚，原因为 `has latch: use step` |
| `step(uint256 id, bytes state, bytes inputs)` | `0xe8281a1a` | `(bytes newState, bytes outputs)`：由调用方提供状态的一拍，三个向量都按 §5 打包 |

处理器合约还提供会改变链上状态的 `beat(address cpu, uint256 id, bytes inputs)`（`0x1fc0021d`），把状态保存在链上。

流片函数是 `tapeout(bytes netlist, uint32 nIn, uint32 nOut) payable returns (uint256 id)`（`0x7bd3ac1d`）。它依次：要求 `msg.value` 恰好等于常量 `TAPEOUT_FEE`（0.0002 BNB）；检查 §3 第 1–7 条；按本层 NAND、LATCH 数量销毁调用者的晶体管代币（REF 引用的门不会再烧一次）；把网表按 24,000 字节分块存为 SSTORE2；以下一个编号把电路 NFT 铸给调用者。检查顺序是：先查流片费（回滚 `tapeout fee`），再查 §3，最后销毁代币。因此用 `eth_call` 模拟 `tapeout` 时，必须带上 `value` = 0.0002 BNB，且调用地址的余额足够（真实余额，或用 `eth_call` 的状态覆盖设置余额），才能走到 §3 的检查。此时不合法网表以 §3 的原因回滚；合法网表在调用者没有代币时，于销毁一步回滚（晶体管余额不足）。流片费属于实现的一部分，本 TAP 不作规定。

处理器工厂可以列出所有处理器合约：`cpuCount()`（`0xa94da8a7`）和 `cpuAt(uint256 i)`（`0x4bc7cbbd`），按创建顺序从 0 开始，只增不减（见 TAP-10 附录）。

以上选择器是所示函数签名的 `keccak256` 取前 4 字节。`circuitInfo`、`netlist`、`eval`、`step`、`cpuCount` 和 `cpuAt` 已在已部署合约上成功调用；`beat` 和 `tapeout` 会改变状态，没有调用。以上签名和返回类型与已验证源码一致。

一个实现如果拒绝所有 §3 所拒绝的网表，并且对任意合法网表、任意状态和输入，要么返回 §4 的输出与新状态，要么因资源不足（gas、内存或调用深度）而失败，即为**符合本 TAP 的实现**。它不得返回与 §4 不同的结果。已部署合约在这个意义上是符合的：它们不限制 REF 嵌套深度，所以足够深的 REF 链会耗尽 gas 或调用深度，而不会返回错误结果。

### 7. 对工具和验证方的要求

1. 对不可信网表求值的工具，必须在求值前限制总门数和 REF 深度，不得假设短网表求值就便宜。
2. 解码器必须先检查记录长度再读取（§3 第 1 条），不得在校验之前按某个计数字段的大小分配内存。
3. 验证工具应当为读取的每个电路记录：区块号、它的全部 REF 依赖，以及该区块时信标背后的电路实现。
4. 证明电路性质的工具（设计证明审查中的等价性、元件认证、编译器）应当注明所实现的本 TAP 版本。

## 设计理由

- **记录现状，而非重新设计。** 本 TAP 描述的是链上已有的格式，因此现有电路（在区块 124,675,668 时共有 1,169 个处理器合约）全部保持有效。尚未确认的部署行为，文中以 **[待定]** 标出，不做猜测。
- **只能向前引用（LATCH 除外）。** 这样按记录顺序求值一遍总是正确的，单次遍历的成本也可预测。反馈只能通过 LATCH，而 LATCH 的值在一拍开始时就已固定，所以不存在组合环路。
- **REF 的状态为什么是连续的一段。** 这样被引用的子电路可以直接用调用方状态的一个切片求值，不需要每个电路单独存储；状态排布也因此完全由网表决定。
- **为什么低位在前。** 已部署的合约就是这样打包的。元件互联标准草案对元件端口采用同样的打包方式，电路的输出可以直接接入元件的输入，无需转换。

## 测试用例

### 测试向量

`assets/tap-02/vectors.json`（格式 `tap-netlist-vectors/1`）包含：

- **合法网表**：组合电路附完整真值表，时序电路附从全零状态开始的多拍序列，所有位向量按 §5 打包：
  - `nand`、`constants`：单个门；使用信号 0 和 1；
  - `popcount8_3151`：处理器 `0xb1024b89886B9a34Aa4ff5F31C411D708b20a14C` 上电路 #3151 的链上字节（385 字节，55 个 NAND），`nIn = 8`，`nOut = 4`，全部 256 种输入；输出为输入中 1 的个数，低位在前；
  - `toggle`：`d` 向后引用的 LATCH（`q' = q XOR en`），8 拍；
  - `ref_with_state`：一个 LATCH、一个引用 `toggle` 的 REF、一个 NAND；用于锁定 §4 的状态排布和 REF 语义，8 拍。其中使用占位处理器地址 `0x00000000000000000000000000000000000000aa`，由向量中的 `refs` 列表解析。
- **不合法网表**（所有实现都必须拒绝）：未知操作码、记录不完整、NAND 向后引用、`nOut = 0`、输出会是输入（没有元素）、输出个数多于元素产生的信号、REF 输入输出个数不匹配、REF 引用的不是登记处理器上的电路。
- **位打包边界情况**（§5），用 `nand` 电路：填充位置 1、多一个字节、空字节串、只有填充位不同的字节串，各附合约会返回的输出。

`vectors.json` 由 `make_vectors.py` 从参考实现生成，可逐字节复现（SHA-256 `1a02f5cf991c130a22dc6cc6ee93d0f8fe0720afed081665fa8b8018aefd203b`）。其中 `chainVerified` 标记仍为 `false`：这些向量是构造出来的，本身没有送进 `eval`/`step` 对比。它们所表达的格式已按下文在链上验证。

### 与 BNB Smart Chain 主网的对比

2026-09-29 **实测**，只读（仅 `eth_call`，未发送任何交易），区块 124,675,668（节点清理了该区块的状态后，改到 124,675,796），节点 `bsc-dataseed.bnbchain.org`：

- 通过 `cpuCount` / `cpuAt` 从工厂列出全部 1,169 个处理器合约；在其中 6 个合约上抽样 24 个电路：4 个含 LATCH，4 个含 REF，5 个 `nIn = 0`，规模从 1 到 1,204 个门。
- 每个电路：网表解码后重新编码，与原字节一致（24/24）；`circuitInfo` 返回的 `nState` 和 `gateCount` 与解码结果一致（24/24）。
- 每个电路随机取 16 组（状态，输入），分别送入 `step` 和按 §4 实现的模拟器：**384/384 完全一致**（新状态和输出逐位相同）。
- 对 18 个 `nState = 0` 的电路调用 `eval`：**288/288 完全一致**。对 6 个带状态的电路，`eval` 回滚并返回 `has latch: use step`。

完整对比（逐个列出电路，附原始结果）见 `assets/tap-02/chain-verification.{json,md}`。这满足了本草案为进入评审设定的条件：至少 20 个主网电路，其中至少 3 个含 LATCH、3 个含 REF。

## 安全考虑

- **求值成本不受网表大小限制。** 一个 REF 只占 31 字节，却可以（递归地）展开成任意大小的电路（见 §7 第 1 条）。主网实测（2026-09-29，`bsc-dataseed1.defibit.io`，区块 124,676,926）：对一个 1,204 门的电路调用 `eval`，执行消耗 2,789,919 gas，约每门 2,317 gas。照此计算，一笔 BNB Smart Chain 交易（16,777,216 gas）约能求值 7,000 个门。实测的 `eth_call` 上限：bsc-dataseed 节点 550,000,000 gas，publicnode 50,000,000 gas，分别约合 239,000 和 21,700 个门（*估算*）。
- **解码器处理的是不可信字节**（见 §7 第 2 条）。
- **REF 目标是受信任的代码路径。** 使用 REF 的电路，其含义取决于被引用的电路。处理器合约是信标代理且工厂尚未封存，所以流片后网表及其求值结果仍可能改变（见 §7 第 3 条）。公共节点只保留最近的状态（bsc-dataseed 实测约 128 个区块），固定在某个区块读取的验证工具需要在这个窗口内读完，否则要换到新区块。
- **等价性只在语义之内成立。** 两个电路等价的证明只在 §4 定义的语义下有意义（见 §7 第 4 条）。
